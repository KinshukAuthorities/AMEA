# AMEA quality audit

Audit scope: authored production instructions and helper behavior, including original creation, reconstruction, edits, 2D/3D routing, parallel work, review and delivery. This is a package audit; no new finished animation was produced to prove a universal quality claim.

| Weakness found | Correction in this revision | Practical limit |
| --- | --- | --- |
| A valid export and a collection of review notes could still miss part of the initial request. | Track material requirements and appropriate evidence, then compare the final result against the original request. The optional delivery gate checks declared review methods and required output-frame coverage. | The agent must interpret the request correctly; software cannot infer subjective success or detect every omitted requirement from a manually declared list. Undeclared temporal or spatial coverage is not inferred. |
| Reference generation, package installation and static geometry could be mistaken for a proven animation method. | Test a representative interval through the actual intended production method, final visual treatment, native editing and export before scaling. | Tools and the agent must actually supply the required drawing, modeling, acting, rigging and inspection capabilities. |
| A successful rough did not prove that cleanup, materials or a generated-frame method would retain its quality. | Review a representative finished-method test at useful final framing, including difficult required views and movement. | One test cannot establish every later view; production still needs continuous visual review. |
| Repeated repairs could consume time while reproducing the same visible defect. | Stop repeated full exports, diagnose the cause and test a materially different correction or supported method on a short interval. | An unresolved capability or access gap may require a concrete user decision or handoff. |
| The entrypoint referred to a structural validator without consistently limiting it to the selected software. | Run the applicable helper or equivalent native checks; provide a cross-software evidence gate without inventing another application's records. | Native editability, playback and artistic quality still require actual inspection. |
| Independently acceptable shots could disagree at their joins or lose persistent state. | Check entry/exit state, neighboring transitions, shared timing and integrated final output, using current artifact identities. | Local frame samples alone cannot certify whole-output continuity. |
| A generic pass could close a defect without the right retest. | Material issues declare retest methods, affected artifacts and applicable frame ranges; current matching reviews are required for closure. | Declaring a visual retest does not prove the observations were truthful or the visible defect disappeared. |

The existing safeguards for actual changing poses, design references, context-sensitive sound, resource-aware parallel workers, single-writer ownership and computer-vision repair remain in place. Finishing-only edits retain their scope; quiet or restrained animation does not acquire unwanted action.

Acceptance is stage-specific: planning deliverables use document evidence, rough requests prove the rough production/preview route, and finished-animation requests test the finished method. The audit does not require every task to produce a complete film.

Remaining limits are explicit: AMEA is an instruction and helper package, not an animation-generation model or an installed production studio. Host control, image/drawing tools, usable geometry, speech generation when needed, rendering resources, service access and genuine visual/audio review must be available and verified. Generator errors, subjective taste, ambiguous intent and tool failures cannot be eliminated by stronger wording. The target is a strong first delivery after autonomous internal iteration, with no guarantee of universal first-prompt satisfaction.

Validation should distinguish package integrity and behavioral helper tests from actual animation quality. A passing test suite proves only its tested invariants. Future changes should be driven by observed failures and representative production tests rather than accumulating promises or compulsory steps for every task.
